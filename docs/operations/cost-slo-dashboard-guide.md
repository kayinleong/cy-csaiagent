# Cost + SLO Dashboard Guide
## D2 Customer Service AI Agent Platform

**Dashboard location:** `<APP_HOSTING_URL>/<lang>/usage` (admin only)
**Data source:** `usageRollups` collection — pre-aggregated daily summaries per agent per pillar

---

## 1. What the Dashboard Shows

The admin usage dashboard reads from `usageRollups` only (never raw `usageEvents`). Data is aggregated once per day by the `usage-rollup` lazy-cron job.

### KPI Tiles (top section)

| KPI | Definition | Notes |
|-----|-----------|-------|
| Active Agents | Distinct agent UIDs with at least one usage event in the selected window | 7-day or 30-day window (selector at top right) |
| Total Messages | Sum of `msgCount` across all rollup docs in the window | One message = one complete chat turn |
| Input Tokens | Sum of `inputTokens` across the window | Tokens sent to Claude (billed rate) |
| Output Tokens | Sum of `outputTokens` across the window | Tokens generated by Claude (billed rate) |
| Cache Hit Rate | `cachedInputTokens / (inputTokens + cachedInputTokens)` | Higher = cheaper per turn (cached tokens ~10% of full price) |
| Avg Resolution Time | Mean of `resolutionTimeMs` samples where available | Time from escalation open to resolved; sparse early-pilot |
| Avg Escalation Rate | Mean of `escalationRate` samples | Fraction of turns that triggered an escalation |

### Charts

| Chart | Type | X-axis | Y-axis |
|-------|------|--------|--------|
| Message Volume Trend | LineChart | Date (day) | Total messages |
| Token Usage by Pillar | BarChart | Pillar (coach/finder/reply) | Input + output tokens |

### Per-Agent Table (bottom)

Shows each active agent (truncated UID for privacy), their message count, input/output tokens, and read/write counts for the selected window. Sorted by message count descending.

## 2. Time Window

Use the window selector (top right of the dashboard):
- **7 days** (default) — typical weekly review
- **30 days** — monthly billing estimate

Window is based on `usageRollups` docs where `day >= windowStart`.

---

## 3. Stale Watchdog

If the dashboard shows:
> "Usage rollup has not run in 25+ hours. Last rollup: [relative time]."

This means the `usage-rollup` lazy-cron job has not fired recently. This usually means no authorized user has loaded the platform recently (cron fires on page load).

**To trigger the rollup:** Navigate to any page while logged in as admin. The lazy-cron fires on the next page load after the 24-hour window elapses.

**If still stale after navigation:** See `incident-runbooks.md §1`.

## 4. Cost Estimation

To estimate monthly LLM costs from the dashboard:

1. Note the 30-day **Input Tokens**, **Output Tokens**, and **Cache Hit Rate**.
2. Apply Anthropic's current published pricing (confirm at `anthropic.com/api` — prices change).
3. Formula:
   ```
   Billable input tokens = inputTokens + cacheCreationInputTokens - cachedInputTokens
   Cached tokens       = cachedInputTokens (billed at ~10% of full input rate)
   Cache write tokens  = cacheCreationInputTokens (billed at ~125% of full input rate)
   Output cost         = outputTokens × output_price_per_1M
   ```

**Note on pre-Phase-5 undercount:** For Finder and Reply agents, the rate-limit budget tracking (`messages.tokens`) was based on `final.usage.totalTokens` (last step of multi-step turns) rather than `final.totalUsage` (sum of all steps). The `usageRollups` data correctly uses `final.totalUsage`. However, historical message token counts (before Phase 5 — 2026-06-07) understate the true per-turn cost for Finder/Reply. Account for this when extrapolating historical data. See `PERF-COST.md §6`.

## 5. SLO Monitoring

The platform's target SLOs are proposed in `PERF-COST.md §4` and finalized by Derek. Monitoring:

| SLO | How to check | Expected value |
|-----|-------------|---------------|
| Chat p95 first-token | Load test (k6 against deployed stack) — LIVE-GATED | PROPOSED < 3,000 ms |
| Error rate under load | Load test — LIVE-GATED | PROPOSED < 1% |
| PDPA erasure SLA | `erasureRequests/{reqId}.completedAt - requestedAt` in Firestore | < 72 hours |
| Usage rollup freshness | Stale watchdog on dashboard | Not stale (< 25 hours) |

There is no automated SLO alerting in v1 (no external scheduler). Manual checks are the monitoring mechanism at pilot scale.

---

## 6. Cost-SLO Trade-off Notes

- **Cache hit rate > 60%** is the target for cost efficiency. If cache hit rate is low early in the pilot, it's expected (cache warms up with repeated system prompt use). It should improve as agents use the same pillar repeatedly.
- **High Finder/Reply token counts** are expected — these pillars run multi-step (5 steps per turn). If output token counts look 3–5× higher for Finder/Reply vs Coach, that is correct behavior.
- **Escalation rate** is an early-pilot signal for knowledge-base gaps. A high rate indicates agents are struggling with topics not covered in the KB.

---

## 7. Admin-Only Access

The usage dashboard is accessible only to users with the `admin` custom claim. Non-admins are redirected. If a senior coach needs cost visibility, an admin must extract and share a summary — there is no coach-visible cost view in v1.
