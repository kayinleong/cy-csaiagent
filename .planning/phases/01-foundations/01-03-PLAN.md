<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client SDK → Firestore | A signed-in client can attempt to read/write any collection; Security Rules are the hard boundary |
| Firestore Security Rules → custom claims | Rules trust `request.auth.token.role`/`tenantId`; claims must only be settable server-side (enforced in 01-04) |
| src/firebase/admin.ts → service account | Admin SDK bypasses rules; must never be reachable from a client bundle |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-06 | Information Disclosure | Cross-tenant/cross-agent Firestore read via blanket `auth != null` | mitigate | Deny-by-default rules with explicit ownership + `sameTenant()` + role checks per collection; rules-unit-test asserts cross-owner/cross-tenant/non-downline reads are DENIED; grep gate asserts no `auth != null` |
| T-01-07 | Tampering | Client mutating or deleting an audit row | mitigate | `auditLogs` rule `allow create/update/delete: if false`; created only via Admin SDK; rules test asserts client mutation denied |
| T-01-08 | Elevation of Privilege | Admin SDK init reachable from client bundle | mitigate | `admin.ts` is server-only, uses ADC (no secret file read), grep-asserted to not import `app/`/`next`; client uses `client.ts` (public config only) |
| T-01-09 | Information Disclosure | A new collection added later without a rule (open by default trap) | mitigate | Deny-by-default base; rules test enumerates all 14 collections so an unruled collection fails closed and is caught in CI |
</threat_model>
