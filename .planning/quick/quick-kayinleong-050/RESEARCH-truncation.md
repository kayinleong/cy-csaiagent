# RESEARCH — Assistant responses truncated mid-sentence (quick-kayinleong-050)

Second independent report. quick-048 dismissed this as "just where the stream had reached
mid-screenshot" and explicitly recorded "NOT a defect ... No step-budget or maxOutputTokens
change is warranted" (`.planning/quick/quick-kayinleong-048/CLAIM.md`). That dismissal was
wrong, but not in the way the report guessed: the *live* stream is complete. The **stored**
copy is not.

---

## Verdict

**Primary mechanism: `onFinish`'s `final.text` is the LAST STEP's text only, not the whole
turn. The route persists that truncated string to Firestore as the assistant message.**

### The proof chain

**1. `final.text` is last-step-only — confirmed in the installed SDK, not inferred.**

`node_modules/ai/dist/index.mjs:4822-4826` (the one and only `onFinish` invocation for
`streamText`):

```js
const finalStep = recordedSteps[recordedSteps.length - 1];
await (onFinish == null ? void 0 : onFinish({
  finishReason,
  totalUsage,
  usage: finalStep.usage,
  content: finalStep.content,
  text: finalStep.text,        // ← LAST STEP ONLY
  ...
  steps: recordedSteps         // ← the full turn lives here
}));
```

Corroborated by the types: `node_modules/ai/dist/index.d.ts:1272` declares
`StreamTextOnFinishCallback = (event: StepResult<TOOLS> & { steps, totalUsage })`, and
`index.d.ts:2060` documents `text` as *"The full text that has been generated by **the last
step**."*

**2. The route writes exactly that string to Firestore.**

`app/api/chat/route.ts:635-644`:

```ts
const assistantMsg: MessageDoc = {
  tenantId: TENANT_ID,
  role: 'assistant',
  content: final.text,        // ← last step only
  ...
}
await appendMessage(cid, assistantMsg)
```

Two further sites inherit the same defect:
- `app/api/chat/route.ts:700` — `latestDraft: final.text` into `leadContext/{leadId}.replySlot`
- `app/api/chat/route.ts:771` — `contentHash: final.text` into the audit row

**3. The client, by contrast, accumulates EVERY step.**

`app/[lang]/chat/chat-input.tsx:347-361` appends every `text-delta` across every block,
inserting `TEXT_BLOCK_SEPARATOR` (`'\n\n'`) at each block boundary:

```ts
const addition =
  isNewBlock && assistantContent.length > 0
    ? TEXT_BLOCK_SEPARATOR + textChunk.delta
    : textChunk.delta
assistantContent += addition
```

So **live UI = complete; Firestore = last block only.** That asymmetry is the whole bug, and
it is precisely the ambiguity the reporter could not resolve ("not sure is the ui rendering
issue or backend maximum length").

**4. Multi-block turns demonstrably happen in this app — quick-048 shipped a fix for them.**

quick-048 added `parseTextChunk` + `TEXT_BLOCK_SEPARATOR` specifically because two steps'
text was welding together ("Got it. Let me search now.The search returned results…"). That
is direct empirical proof that turns emit text in ≥2 blocks in production. **Every one of
those turns loses all but its final block the moment it is persisted.**

**5. The user sees the persisted copy on two very ordinary actions.**

- Browser refresh → `app/[lang]/chat/chat-shell.tsx:139-165` restore-on-mount calls
  `loadConversationMessages(storedCid)` (added in quick-046 so a refresh restores the thread).
- History-drawer navigation → `app/[lang]/chat/chat-shell.tsx:181-187`, same call.

Both funnel through `mapConversationMessages`
(`app/[lang]/chat/conversation-messages-map.ts:46-53`), which renders the stored `content`
verbatim. A tester ~10 questions deep who refreshes or scrolls back through history sees
answers with their opening paragraphs missing — "some part of the response is truncated."

### Secondary contributor A — `stopWhen: stepCountIs(5)` can halt on `tool-calls`, and nothing observes it

`app/api/chat/route.ts:595`. If the model spends all 5 steps and step 5 emits partial text
followed by a tool call, the loop halts with `finishReason: 'tool-calls'` and the closing
text is never written. That is a genuine live mid-sentence truncation.

`finishReason` **is** delivered in the `onFinish` payload
(`node_modules/ai/dist/index.mjs:4824`) but the route never reads it — `grep -rn finishReason
src app` hits only `app/api/chat/route.test.ts` and
`app/[lang]/chat/decode-stream-chunk.test.ts`. **There is currently zero server-side
observability for this**, which is exactly why it cannot be ruled in or out from evidence
today. It stays open, and step 1 of the fix plan is to make it falsifiable.

### Secondary contributor B — history-loaded Finder/Reply turns lose their card and render raw JSON

`app/[lang]/chat/message-list.tsx:105,123` gates card rendering on `msg.replyOutput` /
`msg.finderOutput`. Those fields are only ever set by the live decode bridge
(`chat-input.tsx:404-430`). `mapConversationMessages`
(`conversation-messages-map.ts:46-53`) emits only `{id, role, content, citations}` — and
`load-conversation-messages.ts:51-57` reads only `role`/`content`/`citations` from the doc,
never the persisted `routeDecision` (written at `route.ts:640`). So a reloaded Finder/Reply
turn falls through to `MarkdownMessage` at `message-list.tsx:156` and renders the bare JSON
envelope.

**This is the most likely origin of the "~1,500 characters of leaked Finder JSON" in the
report** — and, per the primary finding, it is the *last step's* JSON with its earlier
prose block already discarded. The two defects compound.

## Ruled out

### `maxOutputTokens` — OUT as the cause (but see the hardening note)

`grep -rn "maxOutputTokens" src app` returns **zero** hits in application code (the only
`maxTokens` hits are `src/kb/ingest/chunker.ts` and `src/kb/kb.test.ts`, which are the KB
text chunker — unrelated).

`@ai-sdk/anthropic@2.0.80` therefore applies its per-model default.
`node_modules/@ai-sdk/anthropic/dist/index.mjs:2280`:

```js
const maxTokens = maxOutputTokens != null ? maxOutputTokens : maxOutputTokensForModel;
```

`maxOutputTokensForModel` comes from `getModelCapabilities(modelId)`
(`dist/index.mjs:3470-3533`). Actual values for the model ids this project resolves via
`modelFor()` (`src/llm/provider.ts:43-49`):

| model id (`appConfig/modelConfig`) | pillar(s) | default `max_tokens` |
|---|---|---|
| `claude-sonnet-4-6` | coach, finder, reply | **128,000** |
| `claude-haiku-4-5` | router | 64,000 |
| `claude-opus-4-7` | grader | 128,000 |
| *anything unrecognized* | — | **4,096** (`isKnownModel: false`) |

128,000 output tokens is roughly 500,000 characters. The ~1,500-character Finder envelope is
about 400 tokens — **0.3% of the cap**. The model cannot have been cut by `max_tokens`.
**Ruled out.**

> Latent hazard worth fixing anyway: the 4,096 fallback fires for any model id the provider's
> `.includes()` chain does not recognize. Model ids come from Firestore, which the app does
> not control. If Derek publishes e.g. `claude-3-5-sonnet-20241022`, the cap silently drops
> to 4,096 with no warning. See Fix plan #3.

### Client-side buffer truncation — OUT as the cause, latent gap only

The suspicion is well-founded in shape but not in fact. `chat-input.tsx:312-320`:

```ts
while (true) {
  const { done, value } = await reader.read()
  if (done) break                                    // ← breaks before flushing
  buffer += decoder.decode(value, { stream: true })
  const lines = buffer.split('\n')
  buffer = lines.pop() ?? ''                         // residual held here
  ...
}
// loop ends at :371 — residual `buffer` is never processed, decoder never flushed
```

Both gaps are real: the trailing partial line is dropped, and `decoder.decode()` is never
called without `{stream:true}` to flush a dangling multi-byte sequence.

But neither can fire, because the SSE writer terminates **every** event with `\n\n`.
`node_modules/ai/dist/index.mjs`, `JsonToSseTransformStream`:

```js
transform(part, controller) { controller.enqueue(`data: ${JSON.stringify(part)}\n\n`); },
flush(controller)          { controller.enqueue("data: [DONE]\n\n"); }
```

The stream always ends on a newline, so `lines.pop()` always yields `''`. Even in the
pathological case the loss ceiling is one partial line — it could not remove a paragraph.
**Ruled out as the mechanism; fix as robustness hardening (Fix plan #4).**

### Markdown rendering swallowing content — OUT

`app/[lang]/chat/markdown-message.tsx` performs no truncation: it is a plain
`<ReactMarkdown remarkPlugins={[remarkGfm]} components={components}>` over the full
`content`, with a component map that only restyles elements. No `line-clamp`, no
`max-height`, no `overflow-hidden` on any message bubble.

`grep -rn "line-clamp|truncate|max-h-|slice(0|substring(0" app/[lang]/chat/` finds only:
- `message-list.tsx:79` — `overflow-hidden` on the **scroll container** (a flexbox
  `min-h-0` scroll setup, not a content clip)
- `reply-draft-card.tsx:315` — `max-h-72` on the editable **textarea** (scrollable)
- `truncate` on lead names, conversation titles, project ids — never on message content

The quick-046 fence-pairing bug is not in play here. **Ruled out.**

### `consumeStream()` racing the response stream — OUT

`app/api/chat/route.ts:819` calls `void result.consumeStream()` before
`toUIMessageStreamResponse()`. This does not steal chunks: `fullStream` (and every other
consumer) goes through `teeStream()` (`node_modules/ai/dist/index.mjs:5434-5437`), which
does `const [stream1, stream2] = this.baseStream.tee(); this.baseStream = stream2;` — a
proper tee with independent buffering. **Ruled out.**

## Fix plan

Minimal, per file. #1 and #2 are the claim; #3–#5 are the hardening this bug exposed.

### 1. `app/api/chat/route.ts` — persist the whole turn, not the last step (THE FIX)

Derive the full text from `final.steps` and use it at all three persistence sites. Join with
`'\n\n'` so the stored copy is byte-identical to what the client rendered with
`TEXT_BLOCK_SEPARATOR`.

Add near the top of `onFinish` (before line 632):

```ts
// AI SDK v5: onFinish's `final.text` is the LAST step's text only
// (ai/dist/index.mjs:4822 — `text: finalStep.text`). Every multi-step turn
// (Coach retrieve→answer, Finder parse→search→answer) writes text in more than one
// block, so persisting final.text silently dropped everything before the last block.
// The client joins blocks with TEXT_BLOCK_SEPARATOR ('\n\n'); match it exactly.
const fullText = (final.steps ?? [])
  .map((s) => s.text)
  .filter((t): t is string => typeof t === 'string' && t.length > 0)
  .join('\n\n')
```

Then substitute:
- `:639` `content: final.text` → `content: fullText`
- `:700` `latestDraft: final.text` → `latestDraft: fullText`
- `:771` `contentHash: final.text` → `contentHash: fullText`

**Leave `replyAgentReportedSopGap(final)` at `:724` reading `final.text` unchanged.** It
parses the JSON envelope, which is by contract the last step — feeding it prose-prefixed
text would be a behavior change outside the minimal fix.

*Regression surface to audit:* `extractCitationChunkIds` / `extractFinderProjectIds` /
`extractReplySopIds` already iterate `final.steps` and are untouched. `final.usage` /
`final.totalUsage` are untouched (the documented `REGRESSION-NOTE` at `:748-755` stays
accurate). `appendMessage`'s `MessageDoc` shape is unchanged.

### 2. `app/api/chat/route.ts` — capture `finishReason` (makes contributor A falsifiable)

The SDK already hands it over; the route just never looks. Add inside `onFinish`:

```ts
// A turn that ends on 'tool-calls' exhausted stopWhen: stepCountIs(5) without ever
// writing its closing text — a real mid-sentence truncation with no other symptom.
// 'length' would mean an output-token cap was hit. Counts + enum only, no content.
if (final.finishReason !== 'stop') {
  console.warn('[chat] non-stop finish', {
    pillar,
    finishReason: final.finishReason,
    steps: final.steps?.length ?? 0,
  })
}
```

No PII, no content — enum and counts only, consistent with the existing `onError` logger at
`:620-626`.

### 3. `app/api/chat/route.ts:595` — set an explicit `maxOutputTokens: 8192`

Hardening, **not** the bug fix. Add alongside `stopWhen`:

```ts
maxOutputTokens: 8192,
```

**Justification against observed output.** The largest output actually seen is the ~1,500
character Finder JSON envelope ≈ **400–500 tokens**. A long trilingual Coach answer with
citations runs comfortably under 2,000 tokens. 8,192 is ~4× headroom over the worst observed
case and ~16× over the typical case, while capping runaway cost (aligned with the T-03-30 /
T-04-COST intent already behind `stepCountIs(5)`).

The reason to set it *at all* is not the ceiling but the floor: today the effective cap is a
`.includes()` lookup on a model-id string that lives in Firestore and the app does not
control. An unrecognized id silently yields **4,096** (`isKnownModel: false`,
`@ai-sdk/anthropic/dist/index.mjs:3527-3533`). Pinning 8,192 makes the value explicit,
model-independent, and immune to that trapdoor — without hard-coding a model id, so the
CLAUDE.md model-agnostic constraint is untouched.

### 4. `app/[lang]/chat/chat-input.tsx:312-320` — flush the residual buffer (low priority)

Cannot currently fire, but the code should not depend on a provider's newline discipline:

```ts
const { done, value } = await reader.read()
if (done) {
  buffer += decoder.decode()          // flush any dangling multi-byte sequence
  if (buffer.trim()) processLine(buffer)  // don't drop a final unterminated line
  break
}
```

Requires hoisting the existing `for (const line of lines)` body into a `processLine` helper.

### 5. History-loaded Finder/Reply turns should re-render as cards (separate claim)

`conversation-messages-map.ts:46-53` + `load-conversation-messages.ts:51-57` should read the
persisted `routeDecision` (already written at `route.ts:640`) and use its pillar prefix to
gate `decodeFinderOutput` / `decodeReplyOutput` exclusively — mirroring the live path's
`serverPillar` gating at `chat-input.tsx:403`. Without it, every reloaded Finder/Reply turn
renders raw JSON.

This is a distinct defect from the truncation and should not be bundled into this claim.

## How to confirm

**Cheapest decisive test — no instrumentation, ~60 seconds:**

1. Ask a Coach question that forces retrieval (so the turn is multi-step), e.g. a specific
   D2 policy question.
2. Let it stream to completion. Copy the on-screen answer.
3. **Refresh the browser** (or open the history drawer and reselect the same thread).
4. Compare.

If the restored bubble is **shorter than what was on screen — missing the opening
paragraph(s) rather than the ending** — the primary verdict is confirmed. No logging, no
deploy, no Firebase console needed.

This works because step 3 is the only thing that swaps the live-accumulated text for the
persisted copy (`chat-shell.tsx:139-165` / `:181-187`).

**Equivalent server-side check:** open `conversations/{cid}/messages` in the Firebase console
and diff the assistant doc's `content` against the screen text. Same signal, and it also
confirms which of the two copies is authoritative — the diagnostic the report was reaching
for.

**For secondary contributor A (`stepCountIs(5)`):** ship the one-line `finishReason` warn
from Fix plan #2 and watch App Hosting logs for `finishReason: 'tool-calls'`. Any occurrence
is a confirmed live truncation. Absence over a testing session rules it out. Do not change
the step budget on speculation — quick-043 set it to fix Coach returning EMPTY responses.
