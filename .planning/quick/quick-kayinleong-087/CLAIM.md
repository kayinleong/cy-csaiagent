## What is wrong

CI has been red since at least 2026-09-03, failing at **Install dependencies**, before lint or
tests ever run:

    npm error `npm ci` can only install packages when your package.json and
    npm error package-lock.json ... are in sync.
    npm error Missing: gcp-metadata@7.0.1 from lock file
    npm error Missing: @swc/helpers@0.5.23 from lock file

Pre-existing, not introduced by quick-085/086 — the identical two packages failed run
`8c9b86f9` before those commits were pushed.

The committed lockfile carries different versions than resolution now demands:

| package | in lockfile | required |
|---|---|---|
| `gcp-metadata` | 8.1.2 (+ 6.1.1 nested x2) | 7.0.1 |
| `@swc/helpers` | 0.5.15 | 0.5.23 |

Consistent with a Dependabot bump landing in `package.json` without the lock tree being fully
regenerated (two Dependabot merges — `qs`, `fast-uri` — are adjacent in the run history).

**Why this blocks the current work:** Firebase App Hosting installs dependencies as part of its
build. A repo whose `npm ci` cannot resolve is a repo that cannot deploy, so quick-085's Finder
table cannot reach the user regardless of how well it is verified locally.

## Two wrong turns, both recorded

**Wrong turn 1 — "Dependabot drift."** `npm install --package-lock-only` under npm 11 produced a
**zero-byte diff**, so the lock was not stale *for npm 11*. True, but it hid the real asymmetry.

**Wrong turn 2 — "CI is on the wrong Node."** The CI log warns
`pdfjs-dist requires >=22.13.0, current v20.20.2`, so I bumped the pin to 22 and pushed. **Still
red, identical error.** The engine warning was a red herring; I should have reproduced locally
before pushing a guess.

## What it actually was

The first hypothesis — Dependabot drift — was wrong, and disproving it was the whole diagnosis.
`npm install --package-lock-only` produced **a zero-byte diff**: the lockfile is already exactly
what `package.json` resolves to. So the "Missing from lock file" error had to come from something
resolving *differently*, not from a stale lock.

**An npm-major mismatch.** Reproducing `npm ci` in an isolated copy of just `package.json` +
`package-lock.json` settled it:

| npm | result against the committed lock |
|---|---|
| 11.11.0 (local, Node 24) | **succeeds** — 1595 packages |
| 10.8.2 (CI, Node 20/22) | **fails** — "Missing … from lock file" |

npm 11 hoists and dedupes three transitive dependencies that npm 10 insists on recording as
explicit **nested** entries. The lock was generated by npm 11, so those entries were absent and
npm 10 refused it. Regenerating with npm 10 adds exactly three lines of tree:

    + node_modules/mongoose/node_modules/gcp-metadata      7.0.1
    + node_modules/next-intl/node_modules/@swc/helpers     0.5.23
    + node_modules/promptfoo/node_modules/@swc/helpers     0.5.23

and **removes nothing** — 1769 → 1772 entries, zero removals, zero top-level changes. The 213
"deleted" lines in the raw diff are JSON key reordering, not lost packages.

The resulting lock installs cleanly under **both** majors (1598 packages each), so it is
forward- and backward-compatible rather than pinned to whoever ran `npm install` last.

## What changed

| file | change | why |
|---|---|---|
| `package-lock.json` | regenerated with `npm@10.8.2 install --package-lock-only` | **the actual fix.** Adds the three nested entries npm 10 requires; installs under npm 10 and npm 11 alike |
| `.github/workflows/ci.yml:21` | `node-version: '20'` → `'22'` | independently correct — `pdfjs-dist` requires `>=22.13.0` and Node 20 was emitting EBADENGINE. Not the cause, kept because the old pin was wrong |
| `package.json` | added `"engines": { "node": ">=22.13.0" }` | nothing declared the requirement, which is why the wrong pin went unnoticed. App Hosting reads `engines.node` for runtime selection |

### Regression surface

- **CI Node 20 → 22:** the only consumer of that pin is the `Lint + Unit Tests + PII Scan` job,
  which previously never got past `npm ci`. It cannot regress a step that never ran.
- **`engines.node`:** advisory to npm by default (`engine-strict` is not set), so it cannot break a
  local install. It *is* read by App Hosting for runtime selection — the intended effect, and the
  reason the deploy is expected to succeed now. Flagged rather than buried: this changes the
  deployed Node runtime from whatever App Hosting defaulted to, to >=22.13.0.
- **Lockfile:** three *nested* additions, no removals, no version changes to any package already
  present. `node_modules` on this machine was left untouched; the gates below ran against it
  unchanged, and the isolated `npm ci` runs are what prove the lock itself.
- **Not touched:** no application code, no dependency ranges in `package.json`.
